# Kustomize Secret Management

## Overview

This project uses Kustomize's `secretGenerator` to manage secrets for Kubernetes deployments. Secrets are **NOT stored as static YAML files** in git for security reasons.

## How It Works

### Base Configuration
The base kustomization (`kustomize/base/kustomization.yaml`) contains **NO secret files**. All secrets are generated by environment-specific overlays.

### Environment Overlays
Each overlay (staging/production) defines its own secrets using `secretGenerator`:

```yaml
secretGenerator:
  - name: database-credentials
    literals:
      - db-name=api_staging
      - db-user=postgres
      - db-password=changeme-staging-db-password
      
  - name: api-secrets
    literals:
      - SECRET_KEY=changeme-staging-secret-key
```

## Setup for New Installations

### Option 1: Use Placeholder Values (Development/Testing)
The default `changeme-*` passwords in the kustomization files work for local development:

```bash
# Deploy with default passwords (OK for local testing)
make deploy ENV=staging
```

### Option 2: Generate Secure Secrets (Recommended)
Use the provided script to generate and inject secure random passwords:

```bash
# Generate secure secrets for staging
./scripts/generate-kustomize-secrets.sh staging

# Generate secure secrets for production  
./scripts/generate-kustomize-secrets.sh production

# Then deploy
make deploy ENV=staging
```

The script will:
- ✅ Generate cryptographically secure random passwords
- ✅ Update the kustomization.yaml with new values
- ✅ Create a timestamped backup
- ✅ Validate the kustomize build

### Option 3: Manual Configuration
Edit the overlay kustomization file directly:

```bash
# Edit staging secrets
vim kustomize/overlays/staging/kustomization.yaml

# Replace changeme-* values with your own secure passwords
secretGenerator:
  - name: database-credentials
    literals:
      - db-password=YOUR_SECURE_PASSWORD_HERE
```

## Security Considerations

### For Local/Development
- ✅ Default `changeme-*` passwords are acceptable
- ✅ Secrets are generated dynamically by Kustomize
- ✅ No secret files are committed to git

### For Staging
- ⚠️ Use the secret generator script or set custom passwords
- ⚠️ Consider .gitignore for modified kustomization files if they contain real secrets
- ⚠️ Restrict cluster access

### For Production
**DO NOT use secretGenerator with inline literals for production!**

Instead, use external secret management:

#### Recommended Solutions:

1. **Sealed Secrets** (Bitnami)
   ```bash
   # Install sealed-secrets controller
   kubectl apply -f https://github.com/bitnami-labs/sealed-secrets/releases/download/v0.18.0/controller.yaml
   
   # Encrypt secrets
   kubeseal --format yaml < secret.yaml > sealed-secret.yaml
   ```
   - ✅ Encrypted secrets safe to commit to git
   - ✅ Decryption only in cluster
   - 📚 https://github.com/bitnami-labs/sealed-secrets

2. **External Secrets Operator**
   ```yaml
   apiVersion: external-secrets.io/v1beta1
   kind: ExternalSecret
   metadata:
     name: database-credentials
   spec:
     secretStoreRef:
       name: vault-backend
     target:
       name: database-credentials
   ```
   - ✅ Integrates with Vault, AWS, GCP, Azure
   - ✅ Centralized secret management
   - 📚 https://external-secrets.io/

3. **HashiCorp Vault**
   - ✅ Enterprise-grade secret management
   - ✅ Dynamic secrets, audit logging, rotation
   - 📚 https://www.vaultproject.io/

4. **Cloud Provider Secret Managers**
   - AWS Secrets Manager with IRSA
   - GCP Secret Manager with Workload Identity
   - Azure Key Vault

## Files and Ignore Patterns

### What's in Git
- ✅ `kustomize/base/kustomization.yaml` - Base config (no secrets)
- ✅ `kustomize/overlays/*/kustomization.yaml` - With placeholder passwords
- ✅ `scripts/generate-kustomize-secrets.sh` - Secret generator

### What's in .gitignore
```gitignore
# Static secret files (never committed)
kustomize/**/secrets.yaml
kustomize/**/secrets-*.yaml  
kustomize/**/grafana-secret.yaml
kustomize/**/*-secret.yaml
```

### What You Might Want to Ignore
If you generate real secrets in kustomization files:
```bash
# Add to .gitignore if using real passwords in overlays
kustomize/overlays/production/kustomization.yaml
kustomize/overlays/staging/kustomization.yaml
```

## Comparison with Direct kubectl Deployment

This project supports two deployment methods:

| Feature | Kustomize | Direct kubectl |
|---------|-----------|----------------|
| Secret Files | No static files | `kubernetes/secrets-*.yaml` |
| Secret Generation | `secretGenerator` in overlays | `./scripts/generate-secrets.sh` |
| Git Storage | Overlays with placeholders | Generated files (gitignored) |
| Script | `generate-kustomize-secrets.sh` | `generate-secrets.sh` |

## Troubleshooting

### Error: "no such file or directory: secrets.yaml"
**Cause:** Base kustomization is trying to load static secret files.

**Fix:** Secrets are now generated by overlays, not base. This should be fixed in the latest version.

### Secrets Not Getting Applied
**Check:**
```bash
# Verify secrets are in the build
kubectl kustomize kustomize/overlays/staging | grep -A 10 "kind: Secret"

# Check secret names match deployments
kubectl get secrets -n api-deployment-demo-staging-ns
```

### Need to Rotate Secrets
```bash
# Generate new secrets
./scripts/generate-kustomize-secrets.sh production

# Apply changes
kubectl apply -k kustomize/overlays/production

# Restart pods to pick up new secrets
kubectl rollout restart deployment -n api-deployment-demo-ns
```

## Best Practices

1. ✅ **Use secret generator script** for initial setup
2. ✅ **Rotate secrets regularly** in production
3. ✅ **Use external secret management** for production
4. ✅ **Limit access** to kustomization files with real secrets
5. ✅ **Monitor secret expiry** if using dynamic secrets
6. ✅ **Audit secret access** through RBAC and logging
7. ⚠️ **Never commit** real production secrets to git
8. ⚠️ **Never store secrets** in CI/CD logs or artifacts
